Lab 12 - Performance optimization and frontend code refactoring

Duration: 2 hours. In this lab we explore how to measure and improve frontend performance, optimize images and assets, and refactor HTML/CSS/JS for faster rendering and easier maintenance.

Read the theory sections carefully, then apply the concepts in the lab tasks and document your findings.

On this page: Overview · Theory · Lab setup · Tasks · References.

Overview

Objectives: Understand frontend performance metrics, identify bottlenecks, and refactor code to improve speed and maintainability.

Concepts: FCP, LCP, CLS, Lighthouse analysis, image optimization, CSS refactoring, JavaScript performance, DOM rendering, and lazy loading.

Tasks: Analyze performance with DevTools/Lighthouse, optimize assets, simplify styles, and review JavaScript best practices.

Deliverable: A short report describing the performance issues found and the refactoring improvements applied.

Theory

1. Introduction to frontend application performance

Frontend performance refers to the speed and efficiency with which a web application responds to the user. A slow application harms user experience and can increase abandonment rates. For this reason, performance optimization is an important stage in modern web development.

Performance is influenced by factors such as image size, amount of JavaScript code, number of HTTP requests, and CSS complexity. The browser must download resources, process code, and render the interface, and any blockage can slow the application.

Performance is measured using metrics such as:

  • FCP (First Contentful Paint) — the first content appears on screen;
  • LCP (Largest Contentful Paint) — the time until the main element is displayed;
  • CLS (Cumulative Layout Shift) — the visual stability of the page.

Examples:

  • an LCP over 2.5 seconds is considered poor;
  • a CLS over 0.1 indicates elements that shift on the page;
  • loading a 5MB image for a thumbnail causes noticeable delays.

2. Performance analysis using DevTools and Lighthouse

Performance analysis means identifying the issues that slow down the application. This process is done using tools like Chrome DevTools and Lighthouse, which are available directly in the browser.

Chrome DevTools provides information about requests, JavaScript execution, and the rendering process. The "Network" tab helps identify large or slow resources, while "Performance" shows operations that consume a lot of CPU.

Lighthouse automatically generates reports and optimization recommendations. For instructions on using Lighthouse, refer to Lab 11. Concrete examples:

  • "Reduce unused JavaScript" — the application loads JS files that are not used;
  • "Properly size images" — images are too large;
  • "Eliminate render-blocking resources" — CSS or JS blocks page rendering.

Practical example:

  • the page has a Lighthouse score of 45/100;
  • after optimizing images and minifying JS, the score increases to 85/100.

3. Optimizing images and media resources

Images are among the largest resources loaded by a web application and can significantly affect load time. Optimizing them reduces bandwidth use and improves user experience.

An important method is using modern formats such as WebP or AVIF. For example:

  • JPG image: 3.2MB;
  • same image in WebP: 700KB.

Images should also be resized correctly:

  • wrong: a 4000x3000 image for a 300x200 card;
  • right: an image optimized to the actual display size.

In many cases, using SVG images is more efficient than classic PNG or JPG. SVGs are vector-based, so they can be scaled without quality loss and have very small sizes for icons or logos.

Example:

  • PNG icon: 120KB;
  • same icon as SVG: 8KB.

SVGs can be styled directly with CSS:

svg {
   fill: #3498db;
}

and they can be animated without loading additional files.

Lazy loading allows images to load only when they become visible:

<img src="image.jpg" loading="lazy">

Practical example:

  • the page initially loads 30 images;
  • with lazy loading, only the first 5 visible images load;
  • load time decreases significantly.

4. Refactoring CSS code

CSS refactoring means reorganizing and simplifying styles without changing application functionality. The goal is cleaner and more efficient code.

Large CSS files often contain duplicate styles and complex selectors:

div.container ul li a span {
    color: blue;
}

Very long selectors are harder to maintain and can impact performance. A better alternative is:

.menu-link {
    color: blue;
}

Practical examples:

  • removing duplicate styles can reduce a CSS file from 500KB to 180KB;
  • using CSS variables:
:root {
   --primary-color: #3498db;
}

allows the theme to be changed quickly.

5. Refactoring and optimizing JavaScript code

JavaScript directly affects performance because it runs in the browser. Complex functions and excessive DOM manipulations can cause delays.

Inefficient example:

for (let i = 0; i < 1000; i++) {
   document.body.innerHTML += "<p>Item</p>";
}

This code modifies the DOM 1000 times. A more efficient version uses DocumentFragment:

const fragment = document.createDocumentFragment();
for (let i = 0; i < 1000; i++) {
  const p = document.createElement('p');
  p.textContent = 'Item';
  fragment.appendChild(p);
}
document.body.appendChild(fragment);

Another common issue is adding too many event listeners:

button.addEventListener(...)

Event delegation on a parent container is more efficient.

Practical example:

  • filtering a large table without debounce → lag while typing;
  • using a 300ms debounce → smoother interaction.

Lab setup

For this lab, you only need to accept the Lab 12 assignment in GitHub Classroom. Once the assignment is accepted, you can continue with the performance improvement task.

Tasks

  1. Open the exercise page in a new tab by clicking Exercise page.
  2. Run a Lighthouse performance audit and review the results for FCP, LCP, CLS, and render-blocking resources.
  3. Review the HTML, CSS and JavaScript examples in the theory section, then identify as many frontend performance issues as possible and describe how you would fix them.
  4. Write a short performance report in report.txt with your findings and proposed optimizations.

Make sure your report includes the performance metrics observed, the bottlenecks you identified, and the refactoring changes you recommend.

Push your work

When you are done, push your report.txt file to GitHub. This will be the deliverable for this lab.

What to include in report.txt

  • Performance metrics from Lighthouse and DevTools.
  • Identified problems for images, CSS, JS, and DOM rendering.
  • Suggested code refactorings and asset optimizations.
  • How the improvements should affect speed and user experience.

Extra work

Extra work: Try to identify one additional optimization on a different page in this repository, such as reducing unused CSS or improving image loading, and note it in your report.
